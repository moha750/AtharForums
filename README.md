# مساحة أثر — الموقع الرسمي

منصّة منتديات موظفي **فرع وزارة الموارد البشرية والتنمية الاجتماعية بالمنطقة الشرقية**: الموظف يسجّل
ببريده الرسمي، يختار منتدى يناسب مهارته، وإدارة أثر تدير المنتديات والأعضاء
والفعاليات من لوحة تحكم واحدة.

---

## التشغيل محليًا

```bash
npm install
cp .env.example .env.local   # ثم عبّئ القيم
npm run dev                  # http://localhost:3000
```

### وضع المعاينة بلا قاعدة بيانات

للاطلاع على الواجهة كاملة دون اتصال بـ Supabase (مفيد للتصميم والمراجعة):

```bash
ATHAR_PREVIEW_FIXTURES=1 npm run dev
```

البيانات كلها تجريبية في هذا الوضع، ولا يمنح أي صلاحية.

## إحصاءات الزوار

**التسجيل من الخادم لا من المتصفّح.** `src/proxy.ts` يسجّل كل طلب صفحة داخل
`event.waitUntil`، فلا يتأخّر الزائر ولا يحجب مانعُ إعلانات شيئًا. أدوات القياس
التي تعتمد على نصّ في المتصفّح تفقد بين ١٠٪ و٤٠٪ من الزيارات.

**ما لا يُخزَّن:** عنوان IP. يدخل `analytics_visitor_hash` ويخرج بصمة مملّحة
بملح شهري لا يُقرأ خارج الدوالّ. ولا كوكيز تتبّع — فلا لافتة موافقة.

**الهوية:** زيارات الموظّف المسجَّل دخوله تُربط بحسابه (قرار إداري صريح).
اللوحة تجميعية، وشاشة الأفراد `/admin/analytics/people` مقصورة على
«المشرف الأعلى» وكل فتح لها يُكتب في `audit_log`. `analytics_prune()` يجمّع
الأيام المكتملة ثم يمحو الصفوف الخام بعد تسعين يومًا.

**منع التزوير:** الكتابة تمرّ بدوالّ `SECURITY DEFINER` تطلب
`ANALYTICS_INGEST_KEY`. المفتاح العام وحده لا يكفي لحقن أرقام. المفتاح يجب أن
يطابق الصفّ في `analytics_ingest_key`؛ وبدونه يتعطّل التسجيل بصمت.

**الروبوتات** تُسجَّل بـ `device = 'bot'` وتُستثنى من كل رقم — لتُعرف ولا تُحتسب.

**ألوان الرسوم** (`--chart-1` و`--chart-2`) متحقَّق منها لعمى الألوان وللتباين
مع السطح في الوضعين. أي تبديل يُعاد فحصه قبل الدمج.

## الباركود الديناميكي

الباركود لا يحمل رابط الوجهة أبدًا، بل رابطنا القصير `{QR_ORIGIN}/q/{code}`.
الوجهة صفّ في `qr_links` يُعدَّل بعد الطباعة، وكل مسح يمرّ بـ
`src/app/q/[code]/route.ts` فيُعَدّ ثم يُحوَّل بـ 307 بلا تخزين مؤقّت.
الملصق المطبوع لا يتغيّر أبدًا.

| المسار | الغرض |
|---|---|
| `/q/{code}` | باب المسح: معالج مسار، 307، خارج الوسيط واللغة |
| `/q/{code}/view` | صفحة عرض الملف (صورة أو PDF)، لا تُعَدّ |
| `/q/unavailable` | المجهول والموقوف وعطل القراءة — صفحة واحدة لا تفرّق |
| `/{locale}/qr` | الباركودات المفردة، والحملات، والإنشاء، والتصميم، والإحصاء |
| `/{locale}/qr/oversight` | شاشة المشرف |
| `/{locale}/admin/qr-access` | منح الصلاحيات ومفتاح الرموز المختارة (للمشرفين) |

**الصلاحيات** في `profile_permissions`: `use_qr_generator` (المولّد)،
و`oversee_qr` (الإشراف)، و`qr_org_account` (حساب الجهة — واحد، يرث باركودات
من يُحذف حسابه). كل السياسات تشترط الملكية **و**الصلاحية معًا، فنزع الصلاحية
يقطع الوصول حتى لصفوف صاحبها. والمشرف العام (admin) لا يملكها تلقائيًّا.

**بلا service_role هنا أيضًا.** ما كان يحتاج مفتاحًا يتجاوز الأمان صار:

- **باب المسح** ← `qr_resolve()` بصلاحيات منشئها، تطلب `QR_SERVER_KEY` الذي
  يطابق الصفّ في `qr_server_key` (نمط `analytics_track` نفسه).
- **المخزن** (`qr-files`) ← تذكرة رفع يصكّها الخادم (`qr_issue_upload_ticket`)
  بالمسار `{userId}/{uuid}.{ext}`؛ سياسة الإدراج لا تقبل غيره، والخادم يُرجع
  رابطًا موقَّعًا يرفع إليه المتصفّح. والمحو لا يقبل ملفًّا يشير إليه صفّ —
  يفحصه `qr_file_referenced()` الذي يرى كل الصفوف.
- **استنزاف التنبيهات** ← `qr_alerts_claim/mark/recipients` بالسرّ نفسه.

**أول تشغيل:** بعد تطبيق `0019_qr.sql`، أدرج السرّ نفسه الذي في بيئة الخادم:

```sql
insert into public.qr_server_key (secret) values ('<QR_SERVER_KEY>');
```

ثم امنح الصلاحيات من «لوحة التحكم ← صلاحيات الباركود».

**التنبيه** مطفأ افتراضيًّا (`QR_ALERTS=on` + `SMTP_URL` يشغّلانه). المحفّز
يكتب صفًّا في `qr_alert_outbox` لكل تبديل وجهة ولكل نافذة جدولة تُضاف أو تُعدَّل
(النافذة تبديلٌ للوجهة أيضًا)، وأفعال الواجهة تستنزفه بعد الاستجابة. **إذا شغّلت
التنبيه فشغّل المُجدوِل أيضًا:** من يكتب بجلسته عبر الواجهة البرمجية مباشرةً
يكتب صفّ التنبيه لكن لا يستنزفه أحد غير المُجدوِل. اجعله يستدعي
`GET /api/qr/alerts/drain` كل بضع دقائق بالترويسة
`Authorization: Bearer <QR_CRON_SECRET>` (هذا شكل Vercel Cron نفسه).

**الاختبارات:** `npm test` (التصديق، والرمز، وكشف الآلات والجهاز، وشكل مسار
الملف، والمدى الزمني، ومسح الباركود المرسوم فعلًا بكل إطار ومقاس)، و
`supabase/tests/0019_qr_guards.sql` لحرّاس القاعدة.

**ملفّات المسح** تُحفظ للأبد بلا مهمّة تنظيف. للحذف اليدوي من محرّر SQL:
`select public.qr_prune_scans('2025-01-01');` — غير ممنوحة لأحد.

## قواعد الهوية البصرية

**ترتيب الشعارات.** إذا اجتمع شعار الوزارة وشعار مساحة أثر في صفّ واحد،
**يتقدّم شعار الوزارة ثم يليه شعار أثر** — الجهة الأمّ تسبق المبادرة المنبثقة
عنها. والتقدّم بحسب اتجاه القراءة: يمين الصفّ في العربية، ويساره في الإنجليزية.
استخدم `flex` مع خصائص منطقية (`start`/`end`) لا اتجاهية (`left`/`right`) حتى
ينعكس الترتيب مع اللغة تلقائيًا.

المواضع الخاضعة للقاعدة اليوم: `site-header.tsx` و`site-footer.tsx`. الصفحة
التشويقية تضع الشعارين في صفّين منفصلين فلا تسري عليها.

## الأمن — ما يجب معرفته قبل التعديل

هذه ليست تفاصيل تجميلية؛ تغييرها يفتح ثغرات:

1. **تقييد نطاق البريد مفروض في قاعدة البيانات**، عبر trigger على
   `auth.users` (`enforce_allowed_email_domain`). الفحص في الواجهة تجميلي فقط.
   لا تعتمد عليه وحده.

2. **لا يوجد مفتاح `service_role` في المشروع إطلاقًا.** كل العمليات — بما فيها
   لوحة التحكم — تمرّ عبر جلسة المستخدم وسياسات RLS. لا تُضِف مفتاحًا يتجاوز
   الأمان «لتسهيل الأمر».

3. **الزائر المجهول لا يملك صلاحية على جدول `profiles`** — لا مجرد سياسة
   تمنعه. حتى لو سقطت سياسة سهوًا، الجدول غير ممنوح له أصلًا.

4. **البريد والرقم الوظيفي والجوال لا تُكشف** لبقيّة الموظفين. دليل أعضاء
   المنتدى يمرّ عبر `forum_members_public()` التي تُظهر الاسم والمسمّى
   والمهارات فقط.

5. **المستخدم لا يستطيع ترقية نفسه** — `guard_profile_privileges` يعيد `role`
   و`is_active` إلى قيمتهما السابقة لأي محاولة تعديل من غير مشرف.

6. **رئيس المنتدى يحرّر المحتوى الوصفي فقط** — لا الحالة ولا الطاقة الاستيعابية
   ولا الرابط (`guard_forum_privileged_columns`).

7. **«رئيس المنتدى» و«العضو الأساسي» ليسا سواء.** `is_forum_lead()` لرئيس
   المنتدى وحده وتحكم قرارات الأشخاص؛ `is_forum_staff()` تشمل الفريق الأساسي
   وتحكم المحتوى فقط. لا تخلط بينهما.

8. **`allowed_email_domains` و`bootstrap_admin_emails` للمشرف الأعلى وحده.**
   هذان العمودان يتحكّمان بمن يدخل المنصّة أصلًا، و`guard_site_settings`
   يعيدهما كما كانا لأي مشرف عادي يحاول تغييرهما.

9. **`is_active = false` يوقف الحساب فعلًا** — الدوال المساعدة كلها تفحصه، فلا
   يبقى الموظف المغادر قادرًا على القراءة أو الكتابة.

10. **الحارس قبل السياسة.** النمط المعتمد هنا: مشغّل `BEFORE UPDATE` يثبّت
    الأعمدة التي لا يملكها المستخدم (`guard_membership_self_update`،
    `guard_registration_self_update`)، لأن `WITH CHECK` لا يستطيع تقييد
    عمود بعينه. إن أضفت جدولًا فيه أعمدة حسّاسة، اتبع النمط نفسه.

11. **سجلّ التدقيق يُكتب بمشغّلات `SECURITY DEFINER`** ولا يملك أحد صلاحية
    الإدراج فيه مباشرةً — فلا يُزوَّر ولا يُكتَم.

## قاعدة البيانات

الملفات في `supabase/migrations/` تُنفَّذ بالترتيب في محرّر SQL لدى Supabase:

| الملف | المحتوى |
|---|---|
| `0001_schema.sql` | الجداول والأنواع والفهارس |
| `0002_functions.sql` | الدوال والمشغّلات وتقييد نطاق البريد |
| `0003_rls.sql` | سياسات أمن الصفوف |
| `0004_grants_storage.sql` | الصلاحيات الصريحة ودلاء التخزين |
| `0005_seed.sql` | الإعدادات والمنتديات المقترحة |
| `0006_hardening.sql` | تصحيحات أمنية ووظيفية بعد مراجعة عدائية |
| `0007_analytics.sql` | جداول الإحصاءات ودوالّ التسجيل |
| `0008_analytics_reporting.sql` | دوالّ القراءة والتجميع والاحتفاظ |
| `0009`–`0018` | إعادة التسمية، والمساحات، والبانرات، والأسئلة، والمجلس، والرسائل |
| `0019_qr.sql` | نظام الباركود الديناميكي: الجداول والحرّاس والسياسات والمخزن والتنبيه |

اختبار حرّاس الباركود (داخل معاملة تُلغى، فلا يترك أثرًا):

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/0019_qr_guards.sql
```

لإعادة توليد الأنواع بعد أي تعديل على المخطّط:

```bash
npx supabase gen types typescript --project-id <PROJECT_ID> > src/lib/database.types.ts
```

> ملاحظة: الأنواع مكتوبة كـ `type` لا `interface` — هذا مقصود. الـ interfaces
> لا تحصل على index signature ضمنية في TypeScript، فلا تقبلها أنواع Supabase.

## النشر

المشروع Next.js قياسي بـ `output: standalone` وبلا أي API خاص بمنصّة واحدة.
يعمل على Vercel، وعلى أي خادم يشغّل Node 20.9+، وداخل حاوية Docker.

راجع `docs/DEPLOYMENT.md` للخطوات.
