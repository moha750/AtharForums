# منتديات أثر — الموقع الرسمي

منصّة منتديات موظفي **وزارة الموارد البشرية والتنمية الاجتماعية**: الموظف يسجّل
ببريده الرسمي، يختار منتدى يناسب مهارته، وإدارة أثر تدير المنتديات والأعضاء
والفعاليات من لوحة تحكم واحدة.

---

## التشغيل محليًا

```bash
npm install
cp .env.example .env.local   # ثم عبّئ القيم
npm run dev                  # http://localhost:3000
```

### وضع المعاينة بلا قاعدة بيانات

للاطلاع على الواجهة كاملة دون اتصال بـ Supabase (مفيد للتصميم والمراجعة):

```bash
ATHAR_PREVIEW_FIXTURES=1 npm run dev
```

البيانات كلها تجريبية في هذا الوضع، ولا يمنح أي صلاحية.

## البنية

| المسار | الغرض |
|---|---|
| `src/app/[locale]/` | صفحات الموقع (ar / en) |
| `src/app/api/auth/callback/` | هبوط الرابط السحري — خارج وسيط اللغة عمدًا |
| `src/actions/` | Server Actions: التسجيل، الانضمام، الإدارة |
| `src/lib/supabase/` | عملاء Supabase (متصفّح، خادم، proxy) |
| `src/lib/database.types.ts` | أنواع قاعدة البيانات |
| `supabase/migrations/` | مخطّط قاعدة البيانات وسياسات RLS |
| `messages/` | نصوص الواجهة بالعربية والإنجليزية |

## الأمن — ما يجب معرفته قبل التعديل

هذه ليست تفاصيل تجميلية؛ تغييرها يفتح ثغرات:

1. **تقييد نطاق البريد مفروض في قاعدة البيانات**، عبر trigger على
   `auth.users` (`enforce_allowed_email_domain`). الفحص في الواجهة تجميلي فقط.
   لا تعتمد عليه وحده.

2. **لا يوجد مفتاح `service_role` في المشروع إطلاقًا.** كل العمليات — بما فيها
   لوحة التحكم — تمرّ عبر جلسة المستخدم وسياسات RLS. لا تُضِف مفتاحًا يتجاوز
   الأمان «لتسهيل الأمر».

3. **الزائر المجهول لا يملك صلاحية على جدول `profiles`** — لا مجرد سياسة
   تمنعه. حتى لو سقطت سياسة سهوًا، الجدول غير ممنوح له أصلًا.

4. **البريد والرقم الوظيفي والجوال لا تُكشف** لبقيّة الموظفين. دليل أعضاء
   المنتدى يمرّ عبر `forum_members_public()` التي تُظهر الاسم والمسمّى
   والمهارات فقط.

5. **المستخدم لا يستطيع ترقية نفسه** — `guard_profile_privileges` يعيد `role`
   و`is_active` إلى قيمتهما السابقة لأي محاولة تعديل من غير مشرف.

6. **رئيس المنتدى يحرّر المحتوى الوصفي فقط** — لا الحالة ولا الطاقة الاستيعابية
   ولا الرابط (`guard_forum_privileged_columns`).

7. **«رئيس المنتدى» و«العضو الأساسي» ليسا سواء.** `is_forum_lead()` لرئيس
   المنتدى وحده وتحكم قرارات الأشخاص؛ `is_forum_staff()` تشمل الفريق الأساسي
   وتحكم المحتوى فقط. لا تخلط بينهما.

8. **`allowed_email_domains` و`bootstrap_admin_emails` للمشرف الأعلى وحده.**
   هذان العمودان يتحكّمان بمن يدخل المنصّة أصلًا، و`guard_site_settings`
   يعيدهما كما كانا لأي مشرف عادي يحاول تغييرهما.

9. **`is_active = false` يوقف الحساب فعلًا** — الدوال المساعدة كلها تفحصه، فلا
   يبقى الموظف المغادر قادرًا على القراءة أو الكتابة.

10. **الحارس قبل السياسة.** النمط المعتمد هنا: مشغّل `BEFORE UPDATE` يثبّت
    الأعمدة التي لا يملكها المستخدم (`guard_membership_self_update`،
    `guard_registration_self_update`)، لأن `WITH CHECK` لا يستطيع تقييد
    عمود بعينه. إن أضفت جدولًا فيه أعمدة حسّاسة، اتبع النمط نفسه.

11. **سجلّ التدقيق يُكتب بمشغّلات `SECURITY DEFINER`** ولا يملك أحد صلاحية
    الإدراج فيه مباشرةً — فلا يُزوَّر ولا يُكتَم.

## قاعدة البيانات

الملفات في `supabase/migrations/` تُنفَّذ بالترتيب في محرّر SQL لدى Supabase:

| الملف | المحتوى |
|---|---|
| `0001_schema.sql` | الجداول والأنواع والفهارس |
| `0002_functions.sql` | الدوال والمشغّلات وتقييد نطاق البريد |
| `0003_rls.sql` | سياسات أمن الصفوف |
| `0004_grants_storage.sql` | الصلاحيات الصريحة ودلاء التخزين |
| `0005_seed.sql` | الإعدادات والمنتديات المقترحة |
| `0006_hardening.sql` | تصحيحات أمنية ووظيفية بعد مراجعة عدائية |

لإعادة توليد الأنواع بعد أي تعديل على المخطّط:

```bash
npx supabase gen types typescript --project-id <PROJECT_ID> > src/lib/database.types.ts
```

> ملاحظة: الأنواع مكتوبة كـ `type` لا `interface` — هذا مقصود. الـ interfaces
> لا تحصل على index signature ضمنية في TypeScript، فلا تقبلها أنواع Supabase.

## النشر

المشروع Next.js قياسي بـ `output: standalone` وبلا أي API خاص بمنصّة واحدة.
يعمل على Vercel، وعلى أي خادم يشغّل Node 20.9+، وداخل حاوية Docker.

راجع `docs/DEPLOYMENT.md` للخطوات.
